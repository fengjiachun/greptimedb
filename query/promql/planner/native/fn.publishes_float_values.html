fn publishes_float_values(statement: &Expr, field_type: &DataType) -> bool
Expand description

Whether the existing planner publishes a Float64 for field_type under statement.

Declining is what keeps the two routes’ columns identical, so a shape this rule does not prove is a decline rather than a guess. The shapes it proves, and the existing planner’s site that decides each:

  • parentheses and subqueries are not shapes of their own: they publish what their inner expression publishes,
  • arithmetic binary operators are built by PromPlanner::prom_token_to_binary_expr_builder, which wraps both operands in cast_float - but the cast has to be the first thing that reaches the samples for the answer to stay the same, which is folds_before_cast: <float fold> * 1 is admitted and sum(integer_field) * 1 is not,
  • min/max fold through common_function::aggrs::extremum::Extremum, whose return_type is Float64, and avg, stddev, stdvar, quantile and group through UDAFs that answer Float64 for every numeric input (PromPlanner::create_numeric_aggregate_expr),
  • sum follows DataFusion’s sum, which answers Float64 for a float argument and the argument’s own type for an integer one,
  • the range functions answer Float64: each is a UDF whose value window is a Float64 range (FLOAT_ANSWERING_RANGE_FUNCTIONS).

What is not proved, and why it keeps the existing plan:

  • a bare selector copies the value column’s own type (InstantManipulate::calculate_output_schema),
  • count and count_values fold through count, which answers Int64 for every input,
  • the math functions keep the type they are given (abs(integer_field) is an integer) and so do label_replace/label_join, ceil, floor, round, clamp* and sort*,
  • -x negates a column of its own type, and a comparison without bool filters on one,
  • a set operation hands on the values it was given, and topk/bottomk/limitk keep the samples they pick.
